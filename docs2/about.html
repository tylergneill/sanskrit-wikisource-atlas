A Practical Intro to Wikisource Structure

A Graph of Pages

Wikisource's most basic ontological unit is the page. Pages can freely link to each other, creating a directed graph, with no inherent hierarchy. In order for one page to link to others, as in a table of contents, all connections must be made manually. There is no distinct "subpage" node or relation type.

Breadcrumbs

The way to make a page that is conceptually a "child" or "subpage" automatically link back to its "parent" page is to carefully construct its name so that it is the parent's name, then a slash, then the unique child page name. For example, Wikisource will automatically parse the page name "अग्निपुराणम्/अध्यायः १" and place at the top of that page a link to the related page "अग्निपुराणम्". These auto-generated links are called "breadcrumbs."

Categories: Another Graph

The next basic ontological unit is the Category. Pages can be labeled with any number of Categories. For each Category, Wikisource creates a display page that shows all associated items.

Categories of course also relate to each other, creating their own directed graph. By convention, this graph should be constructed as a simple tree, with a single root, exactly one parent per node, and nothing left out. However, since categorization is done manually, this is not guaranteed, and one category may have multiple parents, and there can even be cycles.

Namespaces

Distinct ontological types exist in different "namespaces". For example, regular pages are in namespace 0 (technically called "Main"), and categories constitute namespace 14. This makes it easy to use the computational backend (API) to request all items of a given type.

OCR "Proofreading" Pipeline Types

Filling in the text content of a Mainspace page is often done manually. Another options provided by Wikisource is the "Proofreading," OCR-based workflow. An image file is uploaded and stored as part of a central "Index" item (namespace 106). Based on the file metadata, Wikisource then creates a table with links for each page.

The first time a user clicks one of those links and saves the resulting page draft, Wikisource creates a "Page" item (namespace 104) inherently linked to the Index and OCRs the page with Tesseract. Users can then use the side-by-side image-and-text viewer to iteratively proofread. When satisfied with a given page, they manually increment the color-coded progress indicator (red -> yellow -> green).

By convention, Index items can be labeled with categories, but Pages should not be. This is because all items with a given category label will show up equally when viewing the category When trying to view category contents, you don't lest the display of category contents be bloated with thousands of individual Pages.

Transclusion

Content of one item can be virtually injected into the content of another by a process known as "transclusion," similar to symbolic links. In particular, a user-facing Mainspace page can transclude relevant ranges of proofreading "Pages." Proofreading can continue gradually, and the Mainspace page will update automatically.

However, nothing guarantees that transclusion is used in this way. Instead, an editor may well copy-paste Page text into a Mainspace page, in which case proofreading corrections will no longer propagate. Only by reading the source code can readers know the difference.

Strategies for Representing Sanskrit Wikisource Data

After fetching the full export, all items are explored in the namespaces Main, Category, Index, and Page. On Mainspace pages, breadcrumbs are mined to establish parent/child relationships. These backconnections allow rolling child subpages up for more concise display.

असंबद्धवर्गीकृतम् (insufficiently categorized content)

Some content is unreachable from the root category — either because it carries no category tag at all, or because every tag it carries points to a category that is itself orphaned from the root (for example, a full parvan-category hierarchy that exists on the live wiki but is never linked in from anywhere reachable). Both cases are swept into one bucket labeled असंबद्धवर्गीकृतम् — deliberately not "अवर्गीकृतम्" (uncategorized), since the second case genuinely does carry a category tag, just not one that connects anywhere. This bucket is fully browsable as its own set of subtrees and loose items, but is excluded from the main tree's own headline size/count totals.

Multiply-filed categories are shown at every location they're filed, cross-linked, with rollups deduplicated so shared content is never double-counted. are listed separately rather than forced into it.

Category membership does not bubble up: a category tag on a deeply nested subpage does not cause its ancestor works to inherit that category. One narrow exception exists — if every subpage under a work shares a category the work itself lacks, that category is inferred onto the work and visibly marked as inferred; this is a display-only convenience and never edits the live wiki.

Categories link to their own parent category the same way any page links to a category — there's no technical enforcement of a single connected structure. In practice this means some categories are orphaned, small clusters can sit disconnected from the main hierarchy, and a category can legitimately have more than one parent.

To help visualize this, this mirror places all orphaned communities and individual items under the artificial label "asaṃbaddhavargīkṛta." Furthermore, when a category is filed under two parents, the mirror shows it at both locations, cross-linked, and it is careful not to double-count contents for the sake of filesize or page counts. When individual Mainspace or proofreading Index items are categorized in ways that do not sit comfortably at a single place in the tree — which is fully expected and proper! — a magnifying glass icon helps the user visualize the item in its multiple locations by populating the search bar.

How byte counts are calculated

The size Wikisource itself reports for a page is just its stored wikitext — markup, templates, and category tags included, and for a page that transcludes another page's content, the transcluding page's own size is tiny regardless of how much text actually displays. Getting a true sense of "how much real text is here" requires parsing the wikitext and stripping all of that overhead out, which is what this mirror's own size figures are built from, rather than repeating Wikisource's raw byte counts as-is.

It also transliterates from Devanagari to IAST in order to enable more meaningful comparison across collections, whose sizes are more usually given in terms of IAST content. Content transliterated as IAST is approximately 60% the filesize of its Devanagari equivalent.

Transclusion and untranscluded OCR content

Many works begin life as a scanned, OCR'd Index item (proofreading namespace) before an editor assembles a finished mainspace page that transcludes the proofread pages. The pipeline parses mainspace wikitext for transclusion tags: if a mainspace page transcludes any content from a given Index item, that Index item is considered sufficiently complete and only the mainspace version is shown. If an Index item is never transcluded anywhere, it's surfaced directly in the category tree instead, explicitly marked as untranscluded/raw OCR content, using its own category tags. This transcluded/untranscluded distinction is deliberately kept separate from proofreading-quality (color-coded) status — a fully proofread work can still be untranscluded if no one has assembled the mainspace page yet.

Rather than listing an untranscluded Index item's individual scanned-page children one by one, the pipeline reads them once to compute a single rolled-up size and latest-change stat, attached to the Index item itself — the same kind of rollup a finished mainspace work gets from its own subpages, so untranscluded works don't misleadingly appear near-empty.

Size computation

Rather than estimating content size with heuristics, the pipeline fully parses each page's wikitext, expands template calls for real (substituting parameters and recursively re-parsing, rather than merely describing that a template was called), evaluates Lua-based (Scribunto) modules where they materially affect visible text, and then runs actual transliteration to produce true byte counts — rather than an estimated Devanagari→IAST expansion factor.

Pipeline stages

The pipeline runs in three decoupled stages, driven monthly by a GitHub Action: fetch (locate, download, and verify the latest dump), build (parse the dump once into per-namespace records, construct the mainspace tree and category graph, detect transclusion, compute sizes and rollups), and publish (materialize the result into this site's data format). Keeping fetch separate from build/publish means the tree-building and size-computation logic can be iterated on locally against an already-downloaded, cached dump without re-fetching it each time.

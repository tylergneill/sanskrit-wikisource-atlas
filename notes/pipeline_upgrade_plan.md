# Pipeline upgrade plan

Stated 2026-07-10 as "catch up and upgrade pipeline," the next phase of work on this repo, building on the project motivation/roadmap (the data-quality problems that motivate it: Wikisource's category structure is hard to browse, disorienting subcategory nesting, no metadata like filesize, no transliteration, and only ~1,195 of 32,279 pages are categorized at all). Order given is priority order, not necessarily implementation order:

1. **Pipeline in git** — done (this repo itself, previously untracked `tools/` scratch work formalized).
2. **Descend more levels into category/page trees** (e.g. Naiṣadhīya) — **done.** `scrape.py` (`fetch_subpages`/`collect_subpages_recursive`) is now enabled unconditionally in `build_skeleton()` (no `recurse_subpages` param, no `--recurse-subpages`/`--no-recurse-subpages` flag). Validated against नैषधीयचरितम् (2 levels deep, 22 subpages) and, critically, बैबल् (Bible) — the harder case that previously tripped Wikimedia's rate limiter reliably. Root cause turned out to be client identification, not request pacing: the scraper's User-Agent lacked contact info, landing it in Wikimedia's 10 req/min "Unidentified" tier instead of the 200 req/min "compliant User-Agent" tier (see https://www.mediawiki.org/wiki/Wikimedia_APIs/Rate_limits). Fixed by adding the repo URL to the User-Agent, confirmed live (60/60 burst requests succeeded vs. tripping by request #11 before). A `--subpage-delay` flag (`0.2`-`0.3` performs well) remains as a secondary pacing knob for this specifically request-volume-heavy loop. Every `make scrape` run now exercises this path; `docs/data/tree.json` and `docs/data/changelog.json` entry #3 reflect the resulting jump (+14,159 pages, +122.9% bytes) as newly-discovered real content. See CLAUDE.md's "Implemented and ENABLED BY DEFAULT" section for full detail.

   **Caveat, not yet resolved:** verification is against the two known documented cases (नैषधीयचरितम्, बैबल्), both confirmed correctly expanded in the committed `tree.json` — not against the whole corpus. A tree-wide check found 535 pages under the `SUBPAGE_PROBE_MAX_BYTES` (5KB) threshold with no subpages discovered; spot-checking their titles suggests most are plausibly genuine short standalone works (stotras, short poems), but this is inference from titles, not confirmed against the live API. If a future session wants to fully close this item out, that spot-check (comparing a sample of these 535 against live `list=allpages` results) is the remaining step.
3. **Consolidate multi-part works into single items** — NOT started. Right now each Wikisource sub-page (e.g. one sarga of a kāvya) is a separate leaf `page` node in `tree.json`; the goal is to group these into one logical work/item in the data model and UI, rather than presenting fragments.
4. **Compile latest-change datestamps per item** — **implemented and confirmed working.** `fetch_page_meta()` fetches `rvprop=size|timestamp` per page (batched); `build_skeleton()` rolls this up as `max()` over all descendant pages into each node's `stats.last_changed`. Confirmed populated in the actual generated `docs/data/tree.json` (root-level `last_changed` present, e.g. `2026-07-10T14:02:54Z`). The index-page-timestamp-is-unreliable finding in CLAUDE.md was the investigation that justified computing this as a rollup rather than reading it off index pages directly — that finding is real, but don't mistake it for "still just investigated, not implemented."
5. **Include two more content buckets**: OCR output, and uncategorized pages. NOT started — prototype logic exists in `notes/get_uncategorized.ipynb` only. Ties directly to the data-quality finding that only ~1,195 of 32,279 pages are categorized — current scraper only walks the category tree from ग्रन्थाः/धर्मशास्त्रम्, so anything uncategorized or OCR-only is invisible to it. This is the big one for closing the "conservatism" gap.

**2026-07-11 gap audit — quantified how much of the corpus is still outside `tree.json`, and why.** User's hypothesis going in was that item 2 (subpage descent) had probably already pulled most "uncategorized" pages into the tree via their index page's category, making item 5 less urgent than originally scoped. Checked this directly: live `list=allpages` (ns=0) returns 32,419 mainspace titles; the committed `tree.json` has 18,784 distinct page titles — a gap of 13,635 pages (42%), bigger than expected. Broke the gap down by root cause (spot-checking parent index pages' live size/categories against `tree.json`):

- **~3,258 pages, ~56 parent works** — hidden by `SUBPAGE_PROBE_MAX_BYTES` (5,000 bytes). These parent index pages (e.g. `अग्निपुराणम्` 20,836B, `अलङ्कारमणिहारः` 17,732B, `विष्णुस्मृतिः` 16,180B, `वराहपुराणम्` 15,574B, `बृहत्पाराशरहोराशास्त्रम्` 16,737B, `नारदपुराणम्` 12,906B, `शब्दकल्पद्रुमः` 10,835B, `वाचस्पत्यम्` 9,319B, `अंशुमत्काश्यपागमः` 8,459B, `यजुर्वेदभाष्यम्` 8,192B, `शुक्‍लयजुर्वेदः` 7,686B) are correctly discovered via `categorymembers` but are themselves a few KB *over* the gate, so `collect_subpages_recursive` never even probes them — every chapter/section subpage underneath is invisible. This is the caveat flagged in item 2's write-up, now confirmed as a real, non-trivial gap rather than a theoretical risk. Cheapest fix: raise `SUBPAGE_PROBE_MAX_BYTES` (real content pages run tens-to-hundreds of KB, so even doubling or tripling the gate to ~15-20KB would likely close most of this at low added request-volume cost) or drop the gate for pages that are themselves direct `categorymembers` (already "paid for" in request terms) and keep it only for the recursive descent into found subpages.
- **~3,462 pages, ~125 parent works** — the parent work's index page is itself never reached by the category walk at all, i.e. never a `categorymember` of anything under ग्रन्थाः/धर्मशास्त्रम्. Two distinct sub-causes found by spot-check: (a) genuinely zero categories on the page itself (e.g. `रामायणम्` 87B/0 cats, `अर्थशास्त्रम्` 109B/0 cats, `गणेशपुराणम्` 372B/0 cats, `जैमिनीयं ब्राह्मणम्` 1,732B/0 cats, `श्रीमद्भागवत महापुराण` 96B/0 cats) — squarely item 5's original target; (b) page *does* carry a category tag, but that category is itself **orphaned** — filed under no parent category at all (confirmed for `वर्गः:गर्ग संहिता`/`वर्गः:संहिता` behind `गर्गसंहिता`, and `वर्गः:वायुपुराणम्` behind `वायुपुराणम्`) — unreachable from a root-down walk no matter how deep subpage descent goes, since the break is at the *category graph* level, not the page level. Also found ~51 cases where the parent index page's real subpages were literally titled with a stray space before the `/` (e.g. `भविष्यपुराणम् /पर्व १ (ब्राह्मपर्व)/अध्यायः ००१`, confirmed live as a real 30,248-byte chapter) — `apprefix` prefix-matching is literal, not whitespace-normalized, so `fetch_subpages("भविष्यपुराणम्", ...)` (no trailing space) never matches these; a genuine, if narrow, Wikisource title-inconsistency gap, not fixable by the size gate at all.
- **~6,653 pages, no `/` in title** — **correction: my first-pass claim that these were mostly out-of-scope was wrong, based on an unrepresentative alphabetical-first sample.** Rechecking properly: only 6 titles have an `Author:` prefix and only 53 start with an ASCII character (total 59 genuinely out-of-scope-looking, e.g. `Bible`, `Main Page`, `Kempegowda International airport`) — the other **~6,600 are ordinary Devanagari titles indistinguishable from real corpus content** (e.g. `अथर्ववेदः सूक्तं १.१`, `अद्वैतसिद्धिसिद्धान्तसारः`, `महाभारतम्-02-सभापर्व-036`). An evenly-strided (not alphabetical-first) live sample of 100 of these found 18% (~1,190 pages extrapolated) *do* carry a category tag — e.g. an entire cluster of pages like `महाभारतम्-02-सभापर्व-036` filed under `वर्गः:महाभारतम्/सभापर्व`, which is itself an **orphaned category** (0 members' worth of parent linkage — confirmed live, filed under nothing), same root cause as the small बृहत्पाराशरहोराशास्त्रम्/गर्गसंहिता-type cases above but apparently at much larger scale: parvan-level categories for the whole Mahābhārata (`वर्गः:महाभारतम्/सभापर्व` alone has 104 members) look to be entirely absent from the tree via this mechanism. This bucket needs the same orphaned-category treatment as the previous one, not exclusion — the true "clearly out of scope" count here is ~59, not ~6,653. ~81 more matched a `N.N.N.N <text>` numeric-index title pattern (e.g. `1.1.1.1 प्रथमा दशतिः`) with zero categories — plausibly a legitimately-uncategorized numbered-fragment series, not yet traced to a parent work.
- **OCR/proofreading pipeline (Index:/Page: namespaces) — a distinct, previously-unexamined root cause, found in response to the user asking specifically about it.** `scrape.py` only ever queries `cmnamespace: "0|14"` and `apnamespace: "0"` — mainspace + Category only. Wikisource's ProofreadPage extension puts scanned-book metadata/ToC in `Index:` (ns 106, अनुक्रमणिका) and per-scanned-page OCR/proofread text in `Page:` (ns 104, पृष्ठम्); neither is queried at all, by design (mainspace is Wikisource's "finished, transcluded" reading text; Index:/Page: are scanning-workflow infrastructure). Confirmed live: **536 `Index:` pages** (536 distinct scanned works) and **127,746 `Page:` entries** (individual scanned-page transcriptions) exist on sa.wikisource.org — bigger in raw page count than the entire current mirror (18,784 pages). Checked all 536 Index: pages for mainspace transclusion via `list=embeddedin&einamespace=0`: **326 already have at least one mainspace transclusion** (i.e. already represented in `tree.json` via their finished mainspace page, confirming the user's transclusion-based dedup idea is sound) — **210 have zero mainspace transclusion**, meaning that scanned/OCR'd work has never been published to a readable page and is completely invisible to the current mirror. Spot-checked two of the 210 for substance via `Page:` subpage count: one (`AshtavakraGitaWithHindiTranslation1911KhemrajPublishers.djvu`) has 208 scanned pages — a full book sitting entirely unpublished — another had just 2, likely a near-empty stub. Size is a wide spread, not uniformly trivial.

**Bottom line on the user's hypothesis:** partially right, partially wrong, and the picture is bigger than the first pass suggested. Subpage descent (item 2) does correctly rescue subpages *whose parent index page it actually reaches and probes* — that part of the reasoning holds. But there are now **four** distinct, confirmed root causes for the remaining gap, not one: (a) item 2's size-gate bug (~3,258 pages, cheap fix), (b) orphaned categories/zero-category pages at the *individual work* level (~3,462 pages, item 5's original framing), (c) orphaned categories at *bulk/cluster* scale — e.g. the Mahābhārata parvan-categories, only found after correcting the mistaken "out of scope" dismissal, likely another ~1,000+ pages, same fix as (b) but larger than expected, (d) the OCR/proofreading pipeline (Index:/Page: namespaces) — 210 confirmed fully-unpublished scanned works, structurally invisible because the scraper has never queried those namespaces at all. (a) is arguably item 2's unfinished business; (b)+(c)+(d) are all legitimately item 5's scope, and together look larger than the original ~3,400-page estimate — likely several thousand pages once (c) and (d) are fully sized.

**User's proposed design for (d), stated 2026-07-11, not yet implemented:** for each of the 536 Index: works, determine (via `list=embeddedin&einamespace=0`, as done above) whether it's already represented in mainspace. If yes, don't present it again (avoid duplicating the polished version). If no, include it in the mirror anyway, presented as a distinct "second-tier" / unpublished-OCR bucket rather than folded into the main tree undifferentiated — i.e. a new node type or flag in `tree.json`'s schema, not just more `page` nodes indistinguishable from curated mainspace content.

**2026-07-11 (later same day) — size-gate gap (a) closed.** `build_skeleton()`'s top-level subpage probe (`scrape.py`, in the `page_members` loop) no longer gates on `SUBPAGE_PROBE_MAX_BYTES` — every direct `categorymember` is now probed for subpages regardless of its own size, since it's already a fetched/known page (one bounded extra request, not exponential). The gate remains in `collect_subpages_recursive` for the unbounded recursive-descent case, where probing every real content page found during recursion would still roughly double request volume. Verified live before running: `अग्निपुराणम्` (20,836B) → 384 subpages, `वाचस्पत्यम्` (9,319B) → 163 subpages, both previously invisible under the old gate. Ran `make scrape`; result confirmed in committed `tree.json`: page count 18,784 → 22,145 (+3,361, matching the ~3,258 estimate — small overshoot expected, since live Wikisource content shifts between an audit spot-check and a later run), and both अग्निपुराणम् (384) and वाचस्पत्यम् (163) subpage counts in the output match the live API exactly. Trade-off knowingly accepted: this adds one `list=allpages` probe request per categorymember tree-wide (not just the ~56 known-bad index pages), and most of those probes return zero subpages (a real content page usually isn't also an index page) — pure top-level exhaustiveness over a raised-threshold heuristic, deliberately chosen over just raising `SUBPAGE_PROBE_MAX_BYTES` to avoid missing a future outlier above any fixed threshold.

**How to apply:** When extending `scrape.py`, `docs/data/tree.json`'s schema, or the frontend, check this list first — new work likely maps onto one of these five roadmap items. Item 2's size-gate fix (a) is now done — see above. Three sub-parts of the 2026-07-11 gap audit remain open: (b) ~3,462 pages behind orphaned-categories/zero-category individual works, (c) ~1,000+ pages behind bulk/cluster-scale orphaned categories (e.g. Mahābhārata parvan categories), (d) 210 confirmed fully-unpublished OCR works in the `Index:`/`Page:` namespaces. (b)+(c) still fit the existing `category`/`page` node shape, just need new crawl entry points beyond ग्रन्थाः/धर्मशास्त्रम्; (d) needs a new node type per the user's second-tier design above, plus a fetch path into ns 104/106 that the scraper has never touched. Do not do a blanket `list=allpages` sweep across all of ns 0 — the ~59 genuinely out-of-scope titles (Author: pages, English meta pages) show that's not a clean net even after excluding the mistaken "6,653 out of scope" overcorrection. Item 3 (consolidation) implies a schema change to `tree.json` (grouping pages under a work) and corresponding frontend rendering changes in `app.js`; user has decided NOT to pursue this for now (2026-07-11) since it would require per-item curation judgment calls they want to avoid. Items 2 and 4 are both done — don't take "confirmed" or "verified" claims at face value from older notes without checking current code/output, but do treat them as shipped, not pending.

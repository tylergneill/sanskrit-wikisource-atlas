# Pipeline upgrade plan

Stated 2026-07-10 as "catch up and upgrade pipeline," the next phase of work on this repo, building on the project motivation/roadmap (the data-quality problems that motivate it: Wikisource's category structure is hard to browse, disorienting subcategory nesting, no metadata like filesize, no transliteration, and only ~1,195 of 32,279 pages are categorized at all). Order given is priority order, not necessarily implementation order:

1. **Pipeline in git** — done (this repo itself, previously untracked `tools/` scratch work formalized).
2. **Descend more levels into category/page trees** (e.g. Naiṣadhīya) — **done.** `scrape.py` (`fetch_subpages`/`collect_subpages_recursive`) is now enabled unconditionally in `build_skeleton()` (no `recurse_subpages` param, no `--recurse-subpages`/`--no-recurse-subpages` flag). Validated against नैषधीयचरितम् (2 levels deep, 22 subpages) and, critically, बैबल् (Bible) — the harder case that previously tripped Wikimedia's rate limiter reliably. Root cause turned out to be client identification, not request pacing: the scraper's User-Agent lacked contact info, landing it in Wikimedia's 10 req/min "Unidentified" tier instead of the 200 req/min "compliant User-Agent" tier (see https://www.mediawiki.org/wiki/Wikimedia_APIs/Rate_limits). Fixed by adding the repo URL to the User-Agent, confirmed live (60/60 burst requests succeeded vs. tripping by request #11 before). A `--subpage-delay` flag (`0.2`-`0.3` performs well) remains as a secondary pacing knob for this specifically request-volume-heavy loop. Every `make scrape` run now exercises this path; `docs/data/tree.json` and `docs/data/changelog.json` entry #3 reflect the resulting jump (+14,159 pages, +122.9% bytes) as newly-discovered real content. See CLAUDE.md's "Implemented and ENABLED BY DEFAULT" section for full detail.
3. **Consolidate multi-part works into single items** — NOT started. Right now each Wikisource sub-page (e.g. one sarga of a kāvya) is a separate leaf `page` node in `tree.json`; the goal is to group these into one logical work/item in the data model and UI, rather than presenting fragments.
4. **Compile latest-change datestamps per item** — **implemented and confirmed working.** `fetch_page_meta()` fetches `rvprop=size|timestamp` per page (batched); `build_skeleton()` rolls this up as `max()` over all descendant pages into each node's `stats.last_changed`. Confirmed populated in the actual generated `docs/data/tree.json` (root-level `last_changed` present, e.g. `2026-07-10T14:02:54Z`). The index-page-timestamp-is-unreliable finding in CLAUDE.md was the investigation that justified computing this as a rollup rather than reading it off index pages directly — that finding is real, but don't mistake it for "still just investigated, not implemented."
5. **Include two more content buckets**: OCR output, and uncategorized pages. NOT started — prototype logic exists in `notes/get_uncategorized.ipynb` only. Ties directly to the data-quality finding that only ~1,195 of 32,279 pages are categorized — current scraper only walks the category tree from ग्रन्थाः/धर्मशास्त्रम्, so anything uncategorized or OCR-only is invisible to it. This is the big one for closing the "conservatism" gap.

**How to apply:** When extending `scrape.py`, `docs/data/tree.json`'s schema, or the frontend, check this list first — new work likely maps onto one of these five items. Item 5 (uncategorized + OCR buckets) implies scraper changes beyond category-tree walking (e.g. `list=allpages` or similar), which is a bigger architectural change than the current single category-recursion approach in `build_skeleton()`. Item 3 (consolidation) implies a schema change to `tree.json` (grouping pages under a work) and corresponding frontend rendering changes in `app.js`. Items 2 and 4 are both done as of 2026-07-10 — don't take "confirmed" or "verified" claims at face value from older notes without checking current code/output, but do treat them as shipped, not pending.
